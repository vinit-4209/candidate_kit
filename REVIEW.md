# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `determine_attendance_date` (starter lines 80-92) | Assumed naive UTC date `punch_utc.date()`. Failed on overnight shifts crossing midnight and punches within 3 hours prior to shift start. | Punching in at 21:55 IST for a 22:00–06:00 shift, or at 01:00 IST past midnight, was assigned the wrong calendar date instead of the shift start date (Rule R1). | Converted the punch instant to Asia/Kolkata (IST), tested candidate shift start dates (today, yesterday, tomorrow), and mapped to the shift whose `[start - 3h, end + 3h]` window encompasses the punch. |
| 2 | `compute_late_minutes` (starter lines 95-108) | Missing or defective 10-minute grace period handling (either treated $\le 10$ min as late, or subtracted grace window from late minutes). | Punching in at 09:10:00 for a 09:00:00 shift returned 10 late minutes instead of 0; punching in at 09:11:00 returned 1 minute instead of 11 (Rule R2). | Evaluated `diff_minutes`. If $\le 10$, return 0. If $> 10$, return exact late minutes (`math.ceil(diff_minutes)`). |
| 3 | `compute_overtime` (starter lines 112-124) | Failed on overnight shifts because it compared clock times directly without handling day rollover. | Punching out at 06:30 IST for a 22:00–06:00 night shift yielded 0 or negative overtime minutes instead of 30 minutes (Rule R3). | Calculated shift duration to establish timezone-aware `shift_end_dt` on the next calendar day when `end < start`, then took `(out_ist - shift_end_dt).total_seconds() // 60`. |
| 4 | `compute_work_hours` (starter lines 128-135) | Used Python standard `round()` which applies Banker's Rounding (round-half-to-even) and float arithmetic errors. | Intervals like 2.625 hours rounded down to 2.62 instead of 2.63, violating standard financial half-up rounding (Rule R8). | Implemented `round_half_up_2` and `round_half_up_4` using Python's `Decimal` with explicit `ROUND_HALF_UP` quantization. |
| 5 | `epoch_ms_to_datetime_utc` & models (starter lines 140-155) | Allowed sub-second millisecond remainders and lacked epoch range validation. | Microseconds leaked into MongoDB ISODate timestamps, corrupting exact second comparisons and index lookups (Rule R1). | Truncated milliseconds via `(ms // 1000) * 1000`, forced `microsecond = 0`, and added Pydantic epoch millisecond bounds (`MIN_EPOCH_MS` to `MAX_EPOCH_MS`). |
| 6 | `POST /attendance/punch-in` (starter lines 320-350) | Concurrency race condition due to naive read-then-write (`find_one` then `insert_one`) without a unique database index. | 5 simultaneous punch-in requests for the same employee and date created multiple duplicate records instead of 1 success and 4 conflicts (Rule R1). | Added unique compound database index `{"emp_code": 1, "date": 1}` (`uq_attendance_emp_date`) and handled `DuplicateKeyError` to return HTTP 409. |
| 7 | `POST /attendance/punch-out` (starter lines 420-455) | Race condition and double punch-out vulnerability due to non-atomic read and write. | Concurrent punch-out calls both saw `punch_out is None` and succeeded, resulting in double updates and corrupted metrics. | Implemented atomic `find_one_and_update({"_id": recent["_id"], "punch_out": None}, ...)` ensuring exactly one request gets 200 and all concurrent or subsequent calls return 409. |
| 8 | `PATCH /attendance/{emp_code}/{date}` (starter lines 490-530) | Missing audit history tracking, lost updates under concurrent regularizations, and failure to clear punches on `ABSENT`/`LEAVE`. | Setting status to `LEAVE` kept previous `punch_in` and `work_hours`; no history was recorded; concurrent edits caused lost updates. | Enforced punch clearing on `ABSENT`/`LEAVE`, computed exact field-level diff `changes`, appended versioned audit entry to `history`, and enforced optimistic concurrency via `$expr: {"$eq": [{"$size": "$history"}, hist_len]}` returning 409 on conflict. |
| 9 | Missing Analytics / In-Memory Logic (starter lines 550+) | Analytics endpoints were missing, stubbed, or pulled full collections into Python memory, causing $O(N)$ memory spikes and `COLLSCAN`. | Slow response times, collection scans (`COLLSCAN`), and memory exhaustion when querying 100k attendance records. | Implemented all 4 analytics endpoints purely as MongoDB aggregation pipelines with indexed `$match`, `$densify` for gap filling, and `$setWindowFields` for competition ranking. |
| 10 | `POST /employees` & Pydantic models (starter lines 210-240) | Exposed internal MongoDB `_id` (`ObjectId`) in JSON responses; Pydantic models permitted extra undeclared fields. | Responses contained `_id` violating API contract; endpoints accepted arbitrary payload properties without error. | Stripped `_id` from all output serializers, and enforced `ConfigDict(extra="forbid")` across all Pydantic request models. |

### Items Looked At and Decided Were NOT Defects:

1. **Synchronous PyMongo Driver**:
   - *Observation*: PyMongo synchronous `MongoClient` is used rather than an async driver like Motor.
   - *Decision*: Not a defect. FastAPI automatically offloads synchronous endpoint handlers to AnyIO's threadpool (`run_in_threadpool`), preventing blocking of the main event loop while maintaining deterministic execution and simpler connection pooling.
2. **String-formatted `date` field (`"YYYY-MM-DD"`) in `attendance_logs`**:
   - *Observation*: Storing `date` as a plain string alongside UTC ISODate timestamps.
   - *Decision*: Not a defect. As mandated by `DATA_MODEL.md`, storing `"YYYY-MM-DD"` partitions attendance by local business day, enabling direct equality matches and index scans without dynamic timezone conversion stages in queries.
3. **Embedded `history` array within attendance documents**:
   - *Observation*: Storing audit trail history directly inside the attendance log rather than a separate collection.
   - *Decision*: Not a defect. Because regularizations occur infrequently (typically 0–3 times per record), keeping the history array embedded provides atomic single-document updates and eliminates costly join stages.
